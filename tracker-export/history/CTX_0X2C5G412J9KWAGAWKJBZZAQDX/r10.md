## Purpose

Define a TypeScript-based GraphScript language, its compiler, and a VS Code explorer. Its graph models functions, classes, and shared state.

## Boundaries

- The first-release planning scope includes the language, compiler, and VS Code graph explorer.
- Implementation, support for existing projects, and a standalone explorer remain out of scope for the first release.
- First-release tooling supports local CLI use and local desktop VS Code on macOS, with Node.js 24 and TypeScript 7. Other operating systems, browser VS Code, and remote workspaces are outside the first-release support guarantee.
- Tests are ordinary files outside the managed graph and GraphScript release output. They import emitted modules and use an existing test runner. Test dependencies do not appear in the graph explorer.
- Published GraphScript libraries are usable with ordinary JavaScript and TypeScript tools. Consumers do not need GraphScript.

## Working Agreements

- Resolve open design questions with the user before treating proposed behavior as settled.
- Provide project setup, node creation, rename, deletion, and builds through both the CLI and VS Code.
- Keep the graph current with saved source changes, including direct edits and Git operations. Preserve stable node identities and report inconsistencies without silently rewriting source.
- Require affected files to be saved before rename or deletion. Refuse conflicts and referenced-node deletion without changing the project. Never overwrite unsaved work.
- A successful rename preserves the stable node ID and updates the readable name, source filename, and imports that resolve to that ID.
- A program build has one entry file and may include internal native ESM modules that must travel with that entry. Program output must preserve module behavior and exclude unreachable graph nodes.
- Both program and library projects can explicitly produce library output for normal module imports. This does not require removal or execution of the program-start file.
- Keep one common alias for local graph imports. Published libraries provide one package-root entry with named exports and generated type declarations. Internal node-module paths are not required public import paths.
- GraphScript source uses the graph alias for project runtime nodes and package imports for external libraries. Relative runtime code imports and file: URL imports in GraphScript source are errors. This does not restrict imports inside external packages or imports generated by the compiler, and is not a sandbox.
- JavaScript library output uses ESM only and keeps external runtime packages as imports with normal dependency declarations.
- Generate required output package metadata without silently changing the source package manifest or overwriting user-authored metadata.
- The VS Code extension uses the project-local compiler. Report missing or unsupported versions without silently installing, upgrading, or substituting a compiler. Keep ordinary source editing available.
- Publication requires repeatable contract and workflow tests, clean artifact installation, ordinary library-consumer checks, and a recorded manual explorer review. Tie evidence to the release artifacts and tool versions. Missing or failed required checks prevent publication; planning approval is not passing test evidence.
